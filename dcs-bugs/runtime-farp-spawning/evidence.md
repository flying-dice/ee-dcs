# Live reproduction evidence

Tested in DCS **2.9.29.27468** (x86_64, MT, Windows), reported by `dcs.log` at launch. The user loaded a minimal Caucasus mission, `farp.miz`, containing one empty Mission Editor stock `FARP`/`FARPS` named `Static FARP-1-1` and no helicopter group or campaign script. Its airbase id was 2, coalition BLUE, and `getParking(true)` returned all four free terminals before the first spawn.

The tests used the same two-AH-64D Mission Editor group table, including type, payload, route, speed `41.666666666667`, `TakeOffParkingHot` / `From Parking Area Hot`, `start_time=0`, and string `parking`/`parking_id` values `"1"` and `"3"`. The only group edits were fresh names, omitted colliding group/unit IDs, horizontally translated coordinates, and first waypoint `helipadId`/`linkUnit` set to the chosen FARP id. All aircraft were created with **`coalition.addGroup(2, Group.Category.HELICOPTER, spec)` directly**. [authored-control.lua](authored-control.lua) and [runtime-farp.lua](runtime-farp.lua) embed the same fixture and observer. They are standalone mission-Lua reproductions; use unique names or reload a disposable mission before rerunning.

The runtime FARP remained present and BLUE after the failure. At t=1260.1, `getParking(true)` included terminals 3 and 1 with `TO_AC=true` and 2/0 with `TO_AC=false`; this API's available list and `TO_AC` field should be reported separately. At t=1317.5 the reused authored pair remained active/airborne while the runtime pair was absent. DCS logged `WARNING FLIGHT: NO ATC COMM HELIPAD + Issue3-Recheck-RuntimeFARP:127500000` at 23:55:09.040 and `Error: Unit [AH-64D]: Corrupt damage model.` at 23:55:32.885 near the failed spawn. The damage-model message also occurred in other AH-64D tests, so its causal role is unknown. No private full log is copied here.

The matched comparison supports **pre-authoring stock FARPs in the `.miz`** as a practical workaround: an empty mission-authored FARP launched both an initial and a recycled dynamic pair. The runtime FARP test failed with that same aircraft spec. Remaining confounds are FARP world location, runtime heliport initialization, and any Mission Editor-created support or warehouse state. The runtime FARP initially reported RED even though the static was added as USA country 2; it was explicitly changed to BLUE before the four-free-pad check and helicopter spawn. This evidence does not isolate which runtime-FARP subsystem caused removal.

## Run the shareable scripts in Mission Editor

Open a **copy** of [farp.miz](farp.miz) in the Mission Editor. For each test, create an `ONCE` trigger with a `TIME MORE` condition and a `DO SCRIPT FILE` action selecting the corresponding Lua file, then save and fly that disposable mission. A simple unattended sequence uses `authored-control.lua` after 1 s, `recycle-authored.lua` after 250 s, `authored-control.lua` again after 320 s, and `runtime-farp.lua` after 500 s. The recycle script destroys only `Issue3-EmptyAuthored-AH64`, polls `getParking(true)` for all four available terminals for up to 60 s, and sets a fresh name for the second authored-control run. Confirm its `ready` log appears before the second control trigger; delay that trigger if needed. The runtime script creates exactly one stock FARP at the recorded clear site and uses the same embedded aircraft table.

The scripts emit bounded `[issue3 ...]` lines to `dcs.log` for the API result, each 0/1/5/30/120 s sample, and birth/takeoff/crash/dead events. Results also remain in mission Lua as `_G.__issue3_results[caseName]`; each observer removes its event handler after 120 s. The packaged logging and recycle wrapper were added **after** the live observations above; their aircraft data and spawn calls match the tested commands, and all three Lua files passed a Lua 5.1 `loadfile` syntax check. No additional live test was run for this packaging step.
