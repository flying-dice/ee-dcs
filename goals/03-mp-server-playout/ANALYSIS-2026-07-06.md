## 1. Entry point & lifecycle

**Two stacked entry points, both in `main.lua`.** `main.lua` is the script the mission trigger runs; it is *not* just wiring — it carries a whole legacy layer of its own.

- `main.lua:479` calls `dynamic_mission_test.start()`.
  - Inside (`main.lua:442-447`) it *conditionally* hands off to `_G.game_loop.start()` **only if a global `game_loop` table exists**. It does not — `game_loop.lua` uses `local game_loop = {}` … `return game_loop` (`game_loop.lua:50,264`) and never assigns `_G.game_loop`. Under `require`, the global is nil, so this branch logs `WARNING: game_loop module not found` and is a dead path in the normal load.
  - It then runs its **own** parallel systems: airbase-to-airbase C-130/IL-76 `run_supply_wave`, `run_heli_wave` (AH-64D/Mi-24V airbase CAP), `run_ground_wave` (perimeter patrols), and schedules them at 600 s / 1800 s / 1800 s (`main.lua:449-476`).
- `main.lua:483-484` then does `require("game_loop"); game_loop.start()` — this is the **real** campaign boot.

Net effect: the campaign game loop starts once (via require at line 484), but a **second, overlapping spawn layer** (`main.lua`'s own supply/CAP/patrol) runs concurrently forever. If anyone ever *did* load `game_loop.lua` in a way that leaks `_G.game_loop` (e.g. a separate `DO SCRIPT FILE`), `game_loop.start()` would run twice and every scheduler below would be **double-registered** — a live footgun the header comments at `main.lua:3-5` and `440-447` actively invite. See §7.

**Re-injection safety.** `campaign_state.lua:43-44` bumps a global `_DMT_GEN` on every load; every scheduled closure captures `my_gen = cs.GENERATION` and self-cancels (`return nil`) when `cs.GENERATION ~= my_gen`. This lets the script be re-injected mid-session (DCS Studio hot-reload) without old timers double-running. It is **per-process only** — a dedicated-server process restart resets everything (see §6e).

## 2. Shared state model

**One singleton.** `campaign_state.lua` returns module `M`; `M.S` is *the* shared state table. Every other module does `local cs = require("campaign_state"); local S = cs.S` and reads/writes `S.*` directly. There is no message bus and (almost) no use of `_G` — communication is via this shared table plus direct `require` calls. `campaign_state` itself has **zero dependencies** (root of the graph, mirrors EECH SESSION+FORCE).

`M.S` keys and their owners (`campaign_state.lua:46-100`):

| Key | Shape | Written by | Read by |
|---|---|---|---|
| `start_time`, `phase`, `game_over`, `winner` | scalars | game_loop, win_condition | all schedulers (kill switch) |
| `base_health[name]` | 0..1 | keysite (damage/capture), keysite_repair (heal), troop (capture) | everyone |
| `base_owner[name]` | side | keysite, troop, capture | everyone (this is the map) |
| `base_pos[name]` | {x,z} | keysite.init_base_state | everyone |
| `base_efficiency[name]` | 0..1 | keysite_repair.tick | troop, reaction, transfer |
| `base_ammo/base_fuel[name]` | 0..100 | keysite_repair | keysite_repair (efficiency calc) |
| `strength[side]` | 0..100 int | cs.recalc_strength | win_condition, attack_waves, ground_forces, heli_war |
| `force_current[side]` | int census | cs.recalc_strength | (diagnostic) |
| `force_reserve[side][role]` | int pools | supply.init/consume/recycle | every spawner |
| `ground_groups[side][gname]` | {grp,target_base,home_base,want} | ground_forces | keysite.try_capture, heli_war, cas artillery, map_overlay |
| `active_tasks[gname]` | task record | register_task (spawners) | reaction (dedup + follow-on) |
| `base_idle_groups[name]` | int | transfer.update_idle_groups | transfer scoring |
| `patrol_groups[name]` | gname | troop | troop dedup |
| `regen_queue[side][atype]` | FIFO list | regen | regen |
| `fow[name][side]` | 0..FOW_MAX | fog_of_war | cas_bai_sead, troop |
| `keysites[kname]` | installation record | installations | attack_waves, cas artillery, win_condition |
| `_recycled[gname]`, `_completed[gname]` | once-guards | supply, reaction | shared across supply+reaction |

**Cross-module abstractions (the "registries"):**
- **Task registry** — `active_tasks` + `register_task/get_task/clear_task/has_task_against` (`campaign_state.lua:120-143`). The EECH `entity_is_object_of_task` proxy; the whole reaction system depends on it. Spawners register at spawn, reaction consumes on BIRTH/LAND/DEAD.
- **Force reserve pools** — `force_reserve[side][role]`, single per-side finite pools seeded per owned base (`supply.lua:46-112`). Monotonic depletion + RTB recycle, no production. `consume_side`/`recycle_side` are the choke point every spawner passes through.
- **FOW store** — `fow[base][side]` raw counters, decayed 30 s, granted by proximity scan (`fog_of_war.lua`).
- **Ground-groups registry** — `ground_groups[side]`, the standing frontline (`ground_forces.lua`), read by capture, artillery, heli anti-armour, overlay.
- **Keysite registry** — the `base_*` family, owned by `keysite.lua`, is effectively the campaign map.
- **Installations registry** — `keysites[kname]` non-airbase targets (`installations.lua`), a *separate* namespace from `base_*` (note the naming clash: `S.keysites` are installations, not airbases).
- **imap layers** — held **module-local** in `imap.lua` (`imap_raw`/`imap_nrm`, `imap.lua:50-51`), *not* in `S`. The one significant piece of state that lives outside the singleton; only reachable via `imap.get()`.

## 6. Multiplayer readiness gap analysis

**(a) Single-player / zero-player assumptions.** The economy is *entirely* AI-driven and does not require any human — in that narrow sense it is robust to zero players. The one zero-population guard is `recalc_strength` returning 50/50 when no units are fielded (`campaign_state.lua:199`), which never triggers in practice (AI always exists). No code path assumes a player *exists*. However, several paths implicitly assume all mobile units are *AI campaign hardware* — see (b).

**(b) How player-controlled units are treated by each subsystem:**
- **supply RTB recycle — verified skips players.** `supply.make_land_handler` bails at `supply.lua:174`: `if u.getPlayerName and u:getPlayerName() then return end`, before recycling/despawning. A human RTB is never folded into the reserve nor `destroy()`ed. Correct. **But** it also depends on `classify_role(gname)` returning non-nil (`supply.lua:173`); player slots won't match the AI name prefixes, so they'd be skipped anyway — the `getPlayerName` guard is belt-and-suspenders.
- **reaction LAND — skips players** (`reaction.lua:452`, same guard). reaction BIRTH does **not** guard players, but only acts on `active_tasks`-registered groups (`reaction.lua:437-439`); a human birth has no task record → no-op. Safe by construction.
- **regen dead handler — NOT player-guarded.** `regen.make_dead_handler` (`regen.lua:138-179`) has no `getPlayerName` check; it relies solely on `classify_group(gname)` returning nil for non-AI names (`regen.lua:149-150`). A downed human aircraft in a group *not* matching an AI prefix is correctly ignored — but this is fragile: any mission-editor client group accidentally named `CAS-…`, `Strike-…`, `Heli…`, etc. would be enqueued and **regenerated as an AI aircraft**, and would also be counted/credited wrongly. Recommend an explicit `getPlayerName` guard here to match supply/reaction.
- **win_condition kill handler — player-agnostic, mostly fine.** `S_EVENT_KILL` degrades the nearest base by kill position regardless of shooter (`win_condition.lua:97-116`). Human kills correctly feed base attrition. No player-specific bug, though a human parked near a friendly base whose weapons kill nearby enemies still damages the *nearest* base which could be the friendly one (pre-existing model limitation, not player-specific).
- **FOW** scans `coalition.getGroups(side)` and grants fog from *any* friendly unit including humans (`fog_of_war.lua:110-140`) — humans helpfully lift fog. Benign/positive.
- **strength census counts humans.** `count_current_hardware` sums every alive unit from `coalition.getGroups` including player slots (`campaign_state.lua:161-177`), so humans tilt balance-of-power and can influence win/loss and `STRENGTH_SURVIVAL` gating. Minor but real — a full server of one coalition could distort the AI economy's offensive posture.
- **transfer idle-group scan** and **CAS/BAI target scan** enumerate `coalition.getGroups`; human aircraft parked near a base inflate `base_idle_groups`, and (importantly) a *human* is never a target since target scans only look at the enemy coalition's groups — a human on the enemy side **would** be scored as a CAS/BAI/anti-armour target (helis/ground engage "Air"/"Helicopters"). That is arguably desirable (AI hunts players) but uncontrolled.

**(c) Player join/leave events.** There is **no** `S_EVENT_PLAYER_ENTER_UNIT` / `S_EVENT_PLAYER_LEAVE_UNIT` handling anywhere, and no slot-lifecycle tracking. The only birth handling is reaction's task-birth path. Mid-campaign join/leave is entirely invisible to the economy. No per-player state, no slot-occupancy accounting, no re-slot handling.

**(d) Dedicated-server API concerns.** Good news: the code uses **no `net.*`** at all — `net` is unavailable in the sanitized mission-scripting environment on a dedicated server, and the port correctly avoids it. APIs in use are all mission-scripting-legal and server-authoritative: `coalition.addGroup`/`addStaticObject`, `timer.scheduleFunction`, `world.addEventHandler`, `land.*`, and the `trigger.action.*` draw/text calls. `trigger.action.outText` (`game_loop.lua:92`, `keysite.lua:291`, `troop.lua:128`, `win_condition.lua:40`) and `markToAll`/`lineToAll` (`map_overlay.lua`) broadcast to all clients and are fine on a dedicated server. One caveat: `map_overlay` redraws every base label every 30 s via `removeMark`+`markToAll` (`map_overlay.lua:84-86`) and clears/redraws column bands — on a populated server this is continuous F-10 mark churn replicated to every client; acceptable but worth watching for mark-ID growth (`next_task_mark` at `map_overlay.lua:42` grows unbounded with task count, one mark per lifetime task, never GC'd unless `remove_task_arrow` is called — and it is **never called** anywhere, so task arrows accumulate forever). That is a slow leak on long MP sessions.

**(e) Persistence / save-resume.** Confirmed **in-memory only.** All state is in `M.S`, a plain Lua table in the mission environment. The `GENERATION` counter handles *hot re-injection* within one process but nothing survives a `DCS_server.exe` restart — campaign resets to OOB. Notably, `types/dcs_studio.d.lua:296-297` documents a `dcs_studio.file` (guarded write-root file I/O) and `dcs_studio.sqlite` (embedded SQLite) available through the native bridge — **an unused persistence avenue**. A save/resume layer would serialize `S.base_*`, `force_reserve`, `active_tasks`, `ground_groups`, `regen_queue`, `fow`, `keysites`, and imap internals, and restore in `game_loop.start()`.

**(f) Player slot provisioning — the hard blocker.** The mission is empty, and **`coalition.addGroup` cannot create human-flyable slots** — dynamically added units are always AI; DCS client/player slots must exist in the `.miz` at load (groups with `skill = "Client"`), or be provided via the 2.9 dynamic-spawn slot feature (which itself requires mission-level enablement and airfield/carrier slot definitions). As written, **no human can ever occupy a flyable slot** on this mission. To make the campaign playable in MP you must either (i) ship a `.miz` that pre-defines client slots at the airbases the port will discover, or (ii) integrate DCS dynamic spawn. Either way there is a coupling problem: the port spawns AI via `TakeOff → From Parking Area` at every friendly base (`attack_waves.lua:145`, etc.), which competes with human slots for parking and can block/relocate spawns on a busy ramp. The economy also has no concept of reserving airframes/parking for humans.

**MP-readiness summary:** clean on the API-hygiene axis (no `net`, server-authoritative spawns, player-guarded recycle/land handlers), but three substantive gaps: **no player slots exist at all** (f), **no join/leave lifecycle** (c), and **no persistence across restarts** (e) — plus the minor human-counted-in-strength (b) and unbounded task-mark leak (d) issues.

## 7. Code-quality / abstraction observations

- **`main.lua` is a second, redundant spawn engine.** Its C-130/IL-76 supply flights, airbase heli-CAP, and perimeter ground patrols (`main.lua:149-476`) overlap conceptually with `supply`/`heli_war`/`troop` in the campaign layer and run in parallel forever, adding uncoordinated air/ground traffic around every base. This layer predates the game loop and should be retired or folded in; it also duplicates helpers (`get_airdromes`, `group_is_alive`, `to_wp`, a second `seq` counter) that already exist in `campaign_state`/`keysite`.
- **Double-start footgun.** The `_G.game_loop` handoff (`main.lua:442`) versus `require("game_loop")` (`main.lua:483`) is confusing and unsafe: header comments instruct loading `game_loop.lua` first "so the global is available," but the module never sets a global. Any setup that does leak the global causes a full double-registration of every scheduler. Pick one path.
- **Namespace collision: `S.keysites` = installations, `S.base_*` = airbases.** Two things called "keysite" in EECH are split across `keysites` (non-airbase) and `base_*` (airbase) with no unifying accessor, forcing every consumer (attack_waves, artillery, win_condition) to special-case `is_installation = (S.base_pos[tname] == nil)` (`attack_waves.lua:90`). A single keysite registry with a `kind` field would remove the branching.
- **Massive duplication of the AC roster and helper closures.** `AC` aircraft tables are re-declared in `attack_waves`, `cas_bai_sead`, `reaction`, `regen`, `troop`, `heli_war` with overlapping type names; `sector_ratio` is copy-pasted verbatim in `cas_bai_sead.lua:128` and `troop.lua:83`; `nearest_base*` / `is_forward` / frontline-distance loops recur in ~6 modules; `classify_role` (`supply.lua:62`) and `classify_group` (`regen.lua:68`) are two hand-maintained copies of the same prefix table that the comments *explicitly warn must stay in sync* — a fragility that should be one shared classifier.
- **imap state lives outside `S`.** Everything else is in the singleton; imap hides `imap_raw`/`imap_nrm` module-locally (`imap.lua:50`), so it can't be snapshotted for persistence or inspected by other modules without going through `get()`. For the save/resume work in §6e this is an extra serialization special-case.
- **Group enumeration is O(bases × groups) per tick in several hot paths.** `transfer.update_idle_groups` (`transfer.lua:57-87`), FOW's per-base-per-side-per-group triple loop (`fog_of_war.lua:94-144`), and imap's per-AA-unit-per-base loops rebuild from `coalition.getGroups` every period. Fine at current scale but will dominate CPU as unit counts grow on a long MP server.
- **`spawn_strike_package` is ~200 lines** (`attack_waves.lua:82-285`) doing striker + escort inline with near-identical route blocks; the CAP/BARCAP/OCA-sweep/CAS/BAI/SEAD spawners repeat the same TakeOff→attack→Land route literal across modules. A shared "spawn flight from nearest base" builder would cut hundreds of lines and centralize the reserve consume/refund pattern (currently hand-repeated with `recycle_side` on every failure branch — easy to leak a pool on a new code path).
- **Task-mark arrows never removed** (`map_overlay.remove_task_arrow` has zero callers), a slow unbounded-ID leak noted in §6d.
- **`win_condition` and reaction lazily `pcall(require, "installations")`** on every kill/tick; cheap due to `package.loaded` caching but obscures the real dependency (installations is a hard dep of the kill handler and artillery). Prefer top-level requires now that the load order is fixed.

Overall the port is faithful and unusually well-annotated (every module cites EECH line numbers), with a clean single-singleton state model. The blockers for the next phase are the empty-mission slot problem, the absence of any player-lifecycle handling, and in-memory-only state — none of which the current architecture accounts for, but all of which are additive rather than requiring a redesign.
